## Your piece: the Windows web view without the WebView2 SDK's header and loader DLL

`src/stdlib/GUI/Windows/Win32Web.c` (the `Shim.ShimWeb` implementation on Windows) includes the WebView2 SDK's `WebView2.h` (from Microsoft's NuGet package, `nix/webview2-sdk-prebuilt.nix`, bound through the `webview2-windows-*` pkg-config records in `src/stdlib/GUI/btrc.toml`) and loads `WebView2Loader.dll`, an SDK artifact a program would have to ship beside itself, to create the environment. The engine itself, the Evergreen WebView2 Runtime, **is** supplied by Windows 11 (the floor for the Windows rows), and COM is an OS API. Replace the two SDK artifacts with first-party code:

1. A first-party header (e.g. `src/stdlib/GUI/Windows/WebView2Interfaces.h`) declaring, in C, exactly the COM interfaces `Win32Web.c` uses — IIDs and vtables — written from the published interface definitions. A vtable must list every slot up to the last method used, in the documented order; slots this code never calls may be declared as opaque `void*` placeholders named for their position. Declare only what is used (`grep -o "ICoreWebView2[A-Za-z0-9]*" Win32Web.c | sort -u`, plus the completed/event handler interfaces it implements, `EventRegistrationToken`, and the enums it names). The pinned SDK header is available for **reference when checking slot order and IIDs** (`nix build .#stdlib-windows-sdk` puts it under `webview2/`); do not copy its text — the result must be a small first-party file. Add a compile-time check in a test (not shipped) that compiles a translation unit including both the SDK header and yours under different names and `_Static_assert`s that every vtable slot offset you declare equals `offsetof` in the SDK's vtable and that each IID's bytes match, so the first-party declarations are proven against the pin without shipping it. That test may use the SDK from the nix build; the stdlib itself must not.
2. A first-party replacement for the loader's `CreateCoreWebView2EnvironmentWithOptions`: find the installed runtime and call into it. The documented discovery: the environment variable `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` if set; else the registry value `pv` (version) / `location` or `EBWebView` under `SOFTWARE\Microsoft\EdgeUpdate\ClientState\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` (the stable runtime's client id; check `HKEY_LOCAL_MACHINE` in the 32-bit view (`KEY_WOW64_32KEY`), then `HKEY_CURRENT_USER`); the runtime's `EBWebView\<x64|arm64|x86>\EmbeddedBrowserWebView.dll` is loaded with `LoadLibraryExW` by **absolute path** (never a search-path load — this is a DLL-planting boundary; verify the path is under the registered install location and use `LOAD_WITH_ALTERED_SEARCH_PATH`), and its export `CreateWebViewEnvironmentWithOptionsInternal(bool checkRunningInstance, int runtimeType, PCWSTR userDataFolder, IUnknown* environmentOptions, ICoreWebView2CreateCoreWebView2EnvironmentCompletedHandler* handler)` is called. Confirm these details against what the pinned loader actually does where you can (strings/imports/exports of `WebView2Loader.dll` and `EmbeddedBrowserWebView.dll` are observable facts; published open-source loader reimplementations document the same sequence) and write down in the report which parts are documented by Microsoft and which are observed behaviour — the latter is a compatibility risk the owner should know about.
3. Remove the `webview2-windows-*` pkg-config records, the `WebView2.h` include, the `LoadLibraryW(L"WebView2Loader.dll")` path and every place the test hosts or bundles copy `WebView2Loader.dll` beside a program (`grep -rn "WebView2Loader\|webview2" tools src nix .github --include=* -l`; you may edit `tools/target_hosts/windows/**` and tests, but list the `nix/*`, `flake.nix` and workflow lines for the integrator). Remove the WebView2 `[[pending]]` row; the dependency check must pass. Add `EmbeddedBrowserWebView.dll` handling to the policy only if needed, as a run-time load of a system component (`[supplied.windows]`), with a comment that the WebView2 runtime ships with Windows 11.

### Proving it
- Cross-build for `windows-x86_64` and `windows-aarch64` with both frontends (see `src/tests/python/test_native_ui_conformance_windows.py` and the Windows GUI/web tests for how programs are built with zig), strict flags, and assert with `DependencyAudit().binary_problems` that the executable imports nothing but system DLLs and that no `WebView2Loader.dll` is referenced (`strings`-style scan of the binary).
- Nothing here can run a Windows GUI: say exactly which tests exercise the web view on a real Windows runner (workflow and job names) so the integrator can dispatch them, and make the failure messages specific (runtime not found, export missing, HRESULT) so a CI log is diagnosable in one pass.
- Stay out of every stdlib package except `src/stdlib/GUI/Windows/` and the Windows rows of `src/stdlib/GUI/btrc.toml` (other workers are in GUI's FreeType and Linux files).
